# À la carte Monorepo Strategy

## 🎯 Overview

This document defines the versioning strategy, tooling, and release management approach for the À la carte monorepo.

**Last Updated:** November 2026
**Status:** Active - Using semantic-release with Conventional Commits
**Key Principle:** Each app is versioned and released independently from its own commit history

## 📦 Monorepo Structure

```
alacarte/
├── .github/
│   └── workflows/
│       ├── pr-snapshot.yml       # PR snapshot builds (tests + QA artifacts)
│       ├── version.yml           # semantic-release per app on master push
│       └── release.yml           # Build & release from api-v*/client-v*/admin-v* tags
├── apps/
│   ├── api/                      # Go REST API (Gin + GORM, Cloud Run + Neon Postgres)
│   │   ├── Dockerfile
│   │   ├── .releaserc            # semantic-release config, tagFormat api-v${version}
│   │   ├── CHANGELOG.md          # auto-generated by semantic-release
│   │   └── ... (Go code)
│   ├── client/                   # Flutter app (Android APK + Web + desktop)
│   │   ├── .releaserc            # tagFormat client-v${version}
│   │   ├── CHANGELOG.md
│   │   └── ... (Flutter code)
│   └── admin/                    # Vite + React 19 SPA
│       ├── Dockerfile            # local dev only; CI ships a static dist/ artifact
│       └── ... (React code)
├── commitlint.config.js          # Commit message validation rules
├── .husky/
│   └── commit-msg                # Runs commitlint when enabled (opt-in)
├── docker-compose.yml            # Root orchestration
├── docs/                         # Centralized documentation (see docs/README.md)
└── README.md                     # Monorepo overview
```

Notes:

- There is **no root `package.json`**; semantic-release lives in `apps/api` and `apps/client`. **commitlint and husky are not declared in any tracked `package.json`**, so the `.husky/commit-msg` hook only works if you install commitlint yourself and set `core.hooksPath` (see [Troubleshooting](#issue-git-hook-not-working)). No workflow runs commitlint.
- The client has **no Dockerfile** — it ships as a signed Android APK artifact, plus web/desktop targets built locally.
- Admin has a Dockerfile for local use, but CI builds a static `dist/` artifact (no Docker release).

## 🛠️ Tooling Stack

### **semantic-release** - Release Management

**Purpose:** Version bumping, tagging, and changelog generation from conventional commits, intended to be fully automated (see the known caveats in [ci-cd-setup.md](/docs/operations/ci-cd-setup.md)).

**Why chosen:** mature plugin ecosystem; per-app `.releaserc`; version bumps derived from commit messages; auto-generated Markdown changelogs; tags pushed automatically on master merge — no release PR step (intended behaviour; see the caveats).

**Configuration:** Each app that has automated releases owns an `.releaserc` at its root:

- `apps/api/.releaserc` → `tagFormat: "api-v${version}"`
- `apps/client/.releaserc` → `tagFormat: "client-v${version}"`
- `apps/admin/` has **no** `.releaserc` — see [Admin Releases](#admin-releases) below.

**Plugins used (api and client):**

| Plugin | Role |
|---|---|
| `@semantic-release/commit-analyzer` | Decides release type from commits (custom `releaseRules`) |
| `@semantic-release/release-notes-generator` | Builds release notes |
| `@semantic-release/changelog` | Writes the app's `CHANGELOG.md` |
| `@semantic-release/git` | Commits the updated changelog: `chore(release): X.Y.Z [skip ci]` |

Note: no npm plugin is used, so the `version` field in each app's `package.json` is **not** updated by releases. The git tag is the source of truth for versions.

### **Conventional Commits** - Commit Format Standard

**Purpose:** Structured commit messages that drive automated versioning.

**Format:**

```
<type>(<scope>): <subject>

type: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert
scope: api, client, admin, deps, ci, docs, release (REQUIRED)
subject: Brief description in lower-case
```

**Version bumps** (per `.releaserc` release rules, for commits matching the app's scope):

- `feat(api):` → **minor** bump for API (2.3.2 → 2.4.0)
- `fix(api):`, `perf(api):`, `refactor(api):` → **patch** bump
- `docs(api):`, `test(api):`, `build(api):`, `ci(api):`, `chore(api):` (or the same with `client`) → **patch** bump (note: these differ from semantic-release defaults, which would not release at all — the project's `releaseRules` explicitly turn them into patch releases)
- `BREAKING CHANGE:` footer → **major** bump
- **Scope only filters the custom patch rules above.** A commit matching none of them falls back to semantic-release's default rules, so `feat` (minor), `fix`/`perf` (patch) and breaking changes release **both api and client** whatever the scope (`@semantic-release/commit-analyzer` default rules; not confirmed by the repo's tags: `api-v2.3.0` has no `client-v2.3.0`). Only `docs`/`chore`/`test`/`build`/`ci`/`refactor` with a non-matching scope, and `style`, are ignored.

**Examples** (subject must be lower-case):

```bash
feat(api): add wine filtering endpoint
fix(client): resolve cache invalidation bug
docs(admin): update deployment guide
chore(deps): bump dependencies
```

### **commitlint** - Commit Message Validation

**Purpose:** Enforce conventional commit format via git hooks.

**Configuration:** (`commitlint.config.js`) — extends `@commitlint/config-conventional` with:

- `scope-enum`: only `api`, `client`, `admin`, `deps`, `ci`, `docs`, `release`
- `scope-empty: never` — scope is required
- `subject-case: lower-case` — lower-case subjects

**Git Hook:** (`.husky/commit-msg`)

```bash
npx --no -- commitlint --edit $1
```

**Result:** With the hook enabled, an invalid message rejects the commit; rewrite and retry. The hook is opt-in: nothing in the repo installs it, and CI does not re-check messages.

### **GitHub Actions** - Build Orchestration

**Purpose:** Skip docs-only PRs; otherwise test and build all apps; release from tags.

**Workflows (all of them — there is no cleanup workflow):**

- `pr-snapshot.yml` - Tests + snapshot builds for PRs
- `version.yml` - Runs semantic-release per app on master push
- `release.yml` - Builds and creates GitHub Releases from version tags

## 📌 Versioning Strategy

### **Independent Releases Per App**

**Approach:**

- Commits in conventional format drive versioning
- On every push to `master`, `version.yml` runs semantic-release sequentially for **api**, then **client**
- Each app's release is computed from the commits since its last tag, using the `.releaserc` rules plus semantic-release's default-rule fallback (scope does not isolate `feat`/`fix`/`perf`; see Version bumps above)
- If no release-worthy commit exists for an app, no new tag or changelog entry is created. The workflow still dispatches `release.yml` for the app's previous tag (see [ci-cd-setup.md](/docs/operations/ci-cd-setup.md) caveats)
- semantic-release pushes the tag (`api-v2.3.3`, `client-v2.2.1`, ...) and the changelog commit

**Example timeline:**

```
2026-06-29 - Merge feat(api): remove legacy item-type code and add cleanup migration
└── API: api-v2.2.2 → api-v2.3.0 (minor bump); admin unchanged (client: see the default-rule fallback above)

2026-06-29 - Merge fix(api): create composite unique index on (user_id, item_id) instead of user_id only
└── API: api-v2.3.0 → api-v2.3.1 (patch bump); admin unchanged (client: see the default-rule fallback above)
```

Current versions are visible via `git tag` — expect them to diverge over time (e.g. `api-v2.3.x` and `client-v2.2.x`; admin tags are pushed manually and may not exist yet).

**Benefits:** zero manual versioning for api and client; per-app changelogs; versions reflect per-app history; commit standards defined by commitlint (opt-in local hook).

**Trade-offs:** deployments must track each app's tag separately; requires disciplined, correctly scoped commit messages; even docs/chore commits scoped to an app trigger a patch release.

### **Admin Releases**

The admin app has no `.releaserc` and no job in `version.yml`. Admin releases are created by **pushing an `admin-v*` tag manually** (or via the `release.yml` `workflow_dispatch` input). Note: a dispatch builds master HEAD under the given tag's version and creates no GitHub Release (see the caveats in [ci-cd-setup.md](/docs/operations/ci-cd-setup.md)); pushing the tag is the reliable path. If admin's release automation is ever brought in line with the other apps, add a `.releaserc` plus a `release-admin` job to `version.yml` and update this doc.

## 🎨 Commit Best Practices

- **Scope always matches the code changed**: `apps/api` → `(api)`, etc. Scope decides which app gets a patch from `docs`/`chore`/`test`/`build`/`ci`/`refactor`; `feat`/`fix`/`perf` release both apps whatever the scope (see Version bumps).
- **Multiple apps changed?** Make multiple scoped commits:

```bash
feat(api): add wine endpoints
feat(client): add wine browsing ui
feat(admin): add wine management interface
```

- **Breaking changes** use a footer:

```bash
feat(api): redesign authentication system

BREAKING CHANGE: oauth flow now requires additional redirect_uri parameter
```

**PR review checklist:**

- ✅ Valid type, required scope from the allowed list, lower-case subject
- ✅ Scope matches the code actually changed
- ✅ `feat` for features, `fix` for bug fixes, `BREAKING CHANGE:` footer where needed

Full walkthrough: [Contributing Guide](../guides/contributing.md).

## 🔄 Developer Workflow

**1. Branch + commit** (checked only if the commit-msg hook is enabled):

```bash
git checkout -b feat/add-wine-filtering
git commit -m "feat(api): add wine filtering endpoint"
git push origin feat/add-wine-filtering
```

**2. PR → snapshot build** (`pr-snapshot.yml`): skips docs-only PRs; runs per-app tests; builds snapshot `pr-{number}.{increment}`; updates a single bot comment on the PR (details in [Snapshot Builds](#-snapshot-builds-for-qa)).

**3. Merge → release** (`version.yml` + `release.yml`):

1. `release-api` job: semantic-release in `apps/api` — bump version, push `api-vX.Y.Z` tag, commit CHANGELOG.md, trigger `release.yml` via `workflow_dispatch`
2. `release-client` job (runs after api): same flow for `apps/client`
3. `release.yml` builds the tag: API Docker image (`{version}` + `latest`) → ghcr.io; client signed release APK; admin static `dist/` (Actions artifact `admin-dist-{version}`). The GitHub Release gets deployment notes and a changelog link, and the client APK is attached (when the release job resolves the tag; see the caveats in ci-cd-setup.md)

## 🎭 Snapshot Builds for QA

### **Snapshot Versions**

**Purpose:** Build and publish every PR commit for manual QA.

**Version format** (`pr-snapshot.yml`):

```
pr-{pr_number}.{increment}
```

- `increment` = number of commits in the PR (`git rev-list --count base...HEAD`), bumped on each new push
- **One snapshot version is shared by all apps in a PR** (it is not derived from app versions)
- Examples: `pr-123.1`, `pr-123.5`

**Artifacts produced:**

| App | Artifact | Where |
|---|---|---|
| API | Docker image `ghcr.io/{owner}/{repo}-api:pr-{n}.{i}` + convenience tag `:pr-{n}-latest` | ghcr.io |
| Client | Debug APK artifact `alacarte-client-pr-{n}.{i}` (30-day retention) | Workflow artifacts |
| Admin | Static `dist/` artifact `admin-dist-pr-{n}.{i}` (30-day retention) | Workflow artifacts |

**PR comment:** A single `github-actions[bot]` comment on the PR lists the snapshot version, commit, build status, and links plus one `docker pull` line for the API image. It is updated in place on each push.

**No automated cleanup:** Snapshot Docker tags on ghcr.io are not pruned by any workflow. Remove stale `pr-*` tags manually via the ghcr.io package page if they accumulate.

### **Snapshots vs Tagged Releases**

| | PR snapshot | Tagged release |
|---|---|---|
| Trigger | PR opened/synchronized | `api-v*` / `client-v*` / `admin-v*` tag push or `version.yml` on master |
| Version | `pr-{n}.{increment}` | Semver from conventional commits |
| Client build | Debug APK artifact | Signed release APK on GitHub Release |
| API build | Docker image on ghcr.io | Docker image `{version}` + `latest` on ghcr.io |
| Changelog | None | App CHANGELOG.md + GitHub Release notes |

## 📝 Changelog Strategy

### **Auto-Generated Markdown Changelogs Per App**

Each released app maintains a standard **Markdown** `CHANGELOG.md` at its root (`apps/api/CHANGELOG.md`, `apps/client/CHANGELOG.md`), generated by `@semantic-release/changelog` and committed back automatically with `chore(release): X.Y.Z [skip ci]`.

**Format:** Keep a Changelog-style sections (`### Features`, `### Bug Fixes`), each entry linking to the commit and PR, plus compare links between tags:

```markdown
## [2.3.0](https://github.com/davidcharbonnier/alacarte/compare/api-v2.2.2...api-v2.3.0) (2026-06-29)

### Bug Fixes

* **api:** disable FK checks during cleanup index migration ([e06799e](https://github.com/davidcharbonnier/alacarte/commit/e06799e...))

### Features

* **api:** migrate from MySQL to Postgres ([...](...))
```

- **Admin has no CHANGELOG.md** (no semantic-release config). Its release notes are generated ad hoc from git history in `release.yml`.
- GitHub Release bodies link to the app's changelog and include deployment information (Docker pull command, APK download, or static-host instructions).

## 🏗️ CI/CD Pipeline

Two stages: **PR snapshots** for QA (tests + `pr-{n}.{increment}` builds, no version bump) and **tagged releases** on master push (semantic-release → tag → build → GitHub Release).

`.github/workflows/`: `pr-snapshot.yml` (stage 1), `version.yml` (stage 2a: semantic-release per app), `release.yml` (stage 2b: build & GitHub Release from tags). `release.yml` can also be triggered manually (`workflow_dispatch`) with an explicit tag — it builds master HEAD under that tag's version and makes no GitHub Release, so pushing the tag is the reliable way to release admin.

## 📋 Common Issues & Solutions

### Issue: Commit rejected by git hook (when enabled)

```bash
git commit -m "feat: add feature"         # ❌ No scope
git commit -m "feat(api): add feature"    # ✅ With scope
git commit -m "feat(api): Add feature"    # ❌ Subject must be lower-case
git commit -m "feat(api): add feature"    # ✅ Lower-case subject
```

### Issue: No tag created after merging to master

**Solution:**

- Check that at least one commit since the app's last tag is releasable (see Version bumps): `feat`/`fix`/`perf`/breaking with any scope, or `docs`/`chore`/`test`/`build`/`ci`/`refactor` with the app's own scope
- Check the `version.yml` run in the GitHub Actions tab for errors
- Remember: `docs`/`chore` commits scoped to an app do release (patch); `docs`/`chore`/`test`/`build`/`ci`/`refactor` with another scope (e.g. `deps`, `release`) and `style` do not. `feat`/`fix`/`perf` release both apps whatever the scope
- Admin never auto-releases — tags must be pushed manually (see [Admin Releases](#admin-releases))

### Issue: Wrong app versioned

**Solution:** Scope selects the app only for docs/chore/test/build/ci/refactor commits; `feat`/`fix`/`perf` bump both apps (default-rule fallback), so api and client versions often move together. Keep one scope per commit, matching the code changed. Track deployments by tag.

### Issue: Git hook not working

**Problem:** Commits not being validated. The hook is opt-in and needs commitlint installed (it is not a declared dependency).

**Solution:**

```bash
npm i -g @commitlint/cli @commitlint/config-conventional  # or any install `npx --no commitlint` can find
ls -la .husky/commit-msg   # Hook must exist
chmod +x .husky/commit-msg # And be executable
git config core.hooksPath .husky  # Ensure husky hooks are wired up
```
